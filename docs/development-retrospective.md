# 开发复盘与跨项目复用清单

整理日期：2026-09-08。

依据：本地主仓库提交记录、开发路线图、发布与培训上线手册，以及“网页版开发”“部署”任务的近期记录。本地主仓库 HEAD 为 `6a8adbb`；其他任务提到的远程与线上版本不完全相同，因此本文总结已有开发经验，不宣称重新验收了当前线上环境。

## 1. 围绕业务闭环切分迭代

本项目有管理、教师、家长多个端。作业只有完成“教师发布 → 家长提交 → 教师批改”，通知只有完成“发布 → 确认 → 查询逐人回执”，才产生完整价值。

可复用规则：每轮选择一个最小业务闭环，先明确角色、动作、数据变化、结果反馈和验收证据，再拆接口与页面任务。不要用页面数量作为完成度。

适用：审批、订单、售后、预约、培训等多人协作系统。前端可以分端实现，验收必须跨端执行。

## 2. 身份、权限、业务状态分别建模

CP-33.1 修复了历史监护关系默认获得接送权的问题；培训媒体也曾进一步收紧到“本人已布置且已解锁课程”。这些实例说明，“认识这个人”“具有某个角色”不足以证明其可以执行特定动作。

可复用规则：服务端同时检查身份、角色、资源归属、显式授权及当前业务状态。新增高影响权限默认关闭，迁移历史数据时不自动扩权。

验收必须包括跨用户、跨组织、未授权、未解锁、撤销后访问等负向场景。隐藏前端按钮只改善体验，不构成授权控制。

## 3. 历史事实不能依赖当前关系重新解释

提交 `e2da86d` 修复了学生转班后历史日报使用当前班级的问题。接送记录也需要保留当时的责任人和上下文。

可复用规则：先区分“当前主数据”和“事件发生时的事实”。涉及归属、责任、金额或规则版本时，保存必要的事件上下文或快照；停用主数据不能破坏历史引用。

适用：员工调岗、客户转交、商品改价、组织调整。快照范围按业务要求决定，不必复制整张主表；历史归属与当前查询权限也应分别判断。

## 4. 并发一致性要落实到事务和数据库

缺勤与接送不能同时构成相互矛盾的事实。本项目使用事务复查及数据库 trigger/advisory lock 维护这类互斥关系；批量操作还需要避免部分成功造成理解偏差。

可复用规则：先写出必须始终成立的业务约束，再选择唯一约束、事务、锁或幂等机制。前端防重复点击不能代替后端一致性。

不是每个项目都需要触发器。应根据实际竞争条件选择最小足够的方案，并验证重复请求、并发冲突和批量失败的结果。

## 5. 报表复用事实来源，读取避免副作用

每日托管报告采用统一实时聚合，报告 GET 不写入，减少三端各算一套造成的口径分歧。

可复用规则：为同一个业务指标定义唯一口径，列表、详情、导出共享它；普通查询不偷偷补数据或推进业务状态。

适用边界：实时运营视图适合聚合；结算单、合同、已签发报告若要求冻结结果，应另建版本或快照。不能把本项目“日报不落快照”推广成所有报表的规则。

## 6. 错误反馈属于功能本身

`ADMIN-TEACHER-CREATE-001` 记录了后台创建教师返回 409，却没有展示失败的情况。手机号重复与培训课程未启用都可能返回 409，单看状态码无法准确定位原因。该问题在路线图中仍标为待修复，本次未修复。

可复用规则：每个提交动作都应包含进行中、防重复、成功反馈和具体失败提示；失败时保留输入。后端提供稳定错误标识与可理解说明，前端不能把不同原因合并成“操作失败”。

排查顺序：界面动作 → 实际请求 → 响应内容 → 服务端规则 → 数据状态。不要看到按钮无反应就先改权限或业务开关。

## 7. 将代码验收、部署验收和业务验收分开记录

现有发布工具通过健康接口的 Git SHA 核对版本，并检查正式登录、开发登录关闭、存储等；文档单独列出真实微信、真机和恢复演练的外部验收。

可复用规则：至少记录“代码已实现、自动验证已通过、目标环境已部署、真实用户已验收”四种状态，并附版本与证据。构建成功不能替代页面交互，H5 不能替代微信登录验证，少量并发结果不能直接作为生产容量结论。

发布时同时确认代码版本、数据库迁移及环境配置，避免检查的是旧容器或错误服务器。

## 8. 测试入口和运行环境提前设计

部署任务中出现了浏览器测试完整教师端、家长端的需求；已部署的教师学院网页与完整教师业务端并非相同范围。

可复用规则：立项时就明确每个应用的名称、用户、功能范围、运行平台、登录方式及测试入口。平台专属能力单独适配，业务测试数据提前准备。

浏览器测试可以降低业务反馈成本，但测试登录必须有访问保护，不能通过公开开发登录绕过正式认证。

## 9. 上线同时交付灰度、备份和恢复能力

培训上线手册采用单校区、少量教师试运行，并规定关闭开关后保留学习与审计数据；数据库与私有媒体按同一恢复点管理。

可复用规则：发布计划包含灰度范围、观测项、停止条件、应用回退和数据恢复方案。功能关闭、代码回退、数据库恢复是不同动作，不应混为一谈。

备份文件存在不代表能够恢复；在隔离环境恢复后应验证数据数量、关联文件和关键业务。迁移回退必须考虑已经产生的新数据。

## 10. 开发收尾包含工作区与文档交接

“网页版开发”任务记录了多个 worktree 完成合并后仍遗留目录的情况，用户难以判断保留哪个；主目录还存在未提交资料。随后通过检查工作区、合并状态和独有文件完成清理，并将 SSH 私钥移出仓库。

可复用规则：使用独立工作区时记录目录、分支、目的、合并状态和清理条件。任务完成后交付唯一明确的主入口；清理前检查未提交文件和未合并内容。

凭据保存在仓库外，配置模板仅含占位值。交接文档记录当前版本、已完成内容、未解决问题、验证证据和下一步，避免旧路线图被误认为现状。

## 新项目可直接采用的开发流程

1. 写出角色、最小业务闭环、首版边界与应用入口。
2. 定义事实模型、权限矩阵、状态转换和历史保留要求。
3. 建立环境配置、测试账号、测试数据及部署入口。
4. 实现一条跨端闭环，同时补齐加载、空态、错误和重复提交反馈。
5. 验证正常路径、越权、重复、并发和历史变化；运行对应平台构建。
6. 固定发布版本，验证迁移、配置、认证和真实文件访问。
7. 小范围业务试用，记录外部验收结果，按风险决定扩大范围。
8. 交付运行与恢复说明，更新未解决问题，清理已完成的临时工作区。
